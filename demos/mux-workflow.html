Nebius × NVIDIA hackathon · architecture as of 28 Sep 2026

MUX workflow

A shared room where a team talks to one coding agent at the same time. Everyone types and votes, one agent builds, and every finished task becomes a checkpoint the room can rewind to.

One agent per room, three parts

Each room has exactly one agent. It is made of a plain Python program that keeps order and two Nemotron models with separate jobs. Only the coder writes files, so edits never collide.

room actor · Python asyncio task

Keeps order

Owns the plan, inbox, files, logs and budget. Applies every change one at a time and writes it to Postgres as an event. Rebuilds itself from those events after a crash.

coordinator · Nemotron 3.5 Lightning

Decides what gets built

Reads each message as it arrives, one at a time, so it sees the other pending messages, and labels it merge, queue, interrupt, conflict or chat. It also owns the plan: it drafts the first one (create_plan, on Super) and adds new requests (add_plan_item). It never sees file contents.

coder · Super, Ultra after 2 failed builds

Decides how to build it

Works through plan items one by one with a fixed toolset and no shell. It builds full-stack apps (React + Vite + Tailwind, a Hono backend, SQLite). Type-check, build and tests run in a Nebius sandbox from a prebuilt starter image.

Coder loop for one task

There are two kinds of pause point. After every LLM turn (a turn boundary) the coder drains the inbox. After every finished plan item (a task boundary) the room saves a checkpoint.

The coordinator's tools can be fields in its JSON output rather than real tool calls. The room actor carries each one out after checking it. Packages come only from the approved list baked into the starter image.

Manual editing

  • Editors can edit code in the Code tab. One person edits a file at a time, and others see "Dan is editing" and a read-only view.
  • A save goes over REST to the room actor, which stores the new version and streams it to everyone.
  • The coder gets a note with the diff at its next turn boundary. If it tries to edit a file that changed since it read it, edit_file fails and it re-reads first, so nobody's work is silently overwritten.
  • Manual edits go into the next checkpoint, and the timeline shows a manual-edit marker.

Token budget

Target: at least 40% fewer tokens per finished task than a naive agent loop on the same models, with the same or better build success. Measured in evals/tokens.

  • Fresh context per task, and a rolling log of at most one page.
  • Tool results the coder has already used shrink to one-line stubs after each turn.
  • Line-range reads, a compact repo map, and search-and-replace edits instead of whole files.
  • Build and test output trimmed to 5 deduplicated errors. Short Tavily results, cached.
  • The right model per job, with reasoning off for simple edits. A stable prompt start so it can be cached.
  • Turn limits and loop detection. The coordinator never sees file contents.

Example: Priya and Dan

Priya (owner): "Build a booking app for my yoga studio, with a backend for bookings." The coordinator drafts 5 tasks, Dan reorders two, Priya approves.

Priya: "Add a login page." Coordinator says queue, and it becomes task 6.

Dan: "Make the buttons blue," while the coder is on the navbar. That's a merge, picked up at the next turn.

Priya: "Buttons should be green." That's a conflict. A vote card opens and the coder moves on to other tasks. Priya overrides with green, and the result is pinned in the log so the agent never brings blue back.

Coder: asks the room "Stripe or a fake checkout?" and works on other tasks. Priya picks fake checkout.

Dan: fixes a heading in Hero.tsx himself. The coder sees his diff at its next turn.

Dan: dislikes task 4 and rewinds to checkpoint 3. Files, plan, preview and log all go back. Later events are greyed out, so the room can move forward again.

Memory and rewind

  • Task log: written at the end of every task. Each one rolls forward what still matters from the previous log and stays about one page.
  • Pinned facts: vote results and owner overrides never drop out of the rolling log.
  • Day log: when a sitting ends, the task logs become one summary of the current state: what the app is, key decisions, conventions, unfinished work. It also rolls from day to day.
  • Rewind: each log is stored with its checkpoint, so rewinding also restores the log. The agent does not remember undone work. A running coder stops at its next turn boundary, and queued messages are re-classified.
